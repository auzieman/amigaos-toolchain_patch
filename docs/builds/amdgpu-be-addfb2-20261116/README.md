# amdgpu dce_v11 on big-endian: host-byte-order framebuffers and ADDFB2 (#35) — 2026-11-16

## Problem

On big-endian, `drm_mode_addfb2_ioctl` refuses every caller unless the driver sets
`drm_mode_config.quirk_addfb_prefer_host_byte_order`. amdgpu does not set it, so on the A1222:

- `DRM_IOCTL_MODE_ADDFB2` returns `EOPNOTSUPP` for every format;
- legacy `ADDFB` 32/24 is recorded as `XRGB8888`, and `dce_v11_0` scans that format with
  `ENDIAN_8IN32`. In other words, the kernel treats `XRGB8888` as host order, which is a
  bug-compatibility interpretation; `XRGB8888` is little-endian by definition.

Display clients therefore need a big-endian special case: legacy ADDFB, plus Mesa's
BGRX8888 config.

## Patch 0037 (against the kernel017 tree)

`0037-amdgpu-dce11-be-host-byte-order-fb.patch`, generated by `make-0037.py`. It changes only
`dce_v11_0.c`, and every change sits under `#ifdef __BIG_ENDIAN`, except one: the
`XRGB8888`/`ARGB8888` case loses its big-endian swap.

1. Sets `quirk_addfb_prefer_host_byte_order`. Legacy ADDFB 32/24 and fbdev then use
   `DRM_FORMAT_HOST_XRGB8888`, which is `BGRX8888` on big-endian, and ADDFB2 is accepted.
2. Gives the primary plane `BGRX8888, BGRA8888, XRGB8888, ARGB8888`. Without this, the
   default `drm_crtc_init()` list (`XRGB8888, ARGB8888`) makes `drm_any_plane_has_format()`
   reject the host-order formats, including fbdev's. `format_default` stays set, as with
   `drm_crtc_init()`.
3. Scanout: `BGRX8888`/`BGRA8888` are host-order XRGB/ARGB. They are programmed as
   ARGB8888 with `ENDIAN_8IN32`, the same register values as before for legacy ADDFB, so
   fbcon and legacy clients see no change. `XRGB8888`/`ARGB8888` are now true little-endian
   (`ENDIAN_NONE`).

Not handled: 16 bpp legacy ADDFB. Its host format, `RGB565 | DRM_FORMAT_BIG_ENDIAN`, is not
in the plane list. Other DCE generations and DC are unchanged.

- **Compiler:** the GCC14 SPE SDK `tabor3` (candidate 0001-0024, including the #46 fix),

## A1222 results

For both runs, amdgpu was loaded with `polaris11_le_user_ib=1`, and userspace was the
tabor3 SPE GL bundle (Mesa 26.2.3, radeonsi/ACO).

- **017 baseline:** the board was not power-cycled first. It had been up about 13.5 h,
  after the full GLES3 dEQP run, with the monitor mode at 3840x2160@30.
- **019:** a power-cycled boot, with the monitor mode at 1920x2160@60.

The raw output is in `hw/`.

`fbfmt.c` fills a dumb buffer with four quadrants (red top-left, green top-right, white
bottom-right, blue bottom-left) and registers it three ways:

| Case | 017 (before) | 019 (0037) | On screen, 019 |
|---|---|---|---|
| 1 legacy ADDFB 32/24, host-order words | ok, recorded `XR24` | ok, recorded `BX24` | correct |
| 2 ADDFB2 `BGRX8888`, host-order words | `EOPNOTSUPP` | ok, `BX24` | correct |
| 3 ADDFB2 `XRGB8888`, little-endian bytes B,G,R,X | `EOPNOTSUPP` | ok, `XR24` | correct |

The colours were checked by eye on HDMI. The fbcon text console on 019 also looked
normal by eye, the same as on 017. Kernel taint stayed 0 throughout.

The other GL tests also passed on 019:

- `gltest`: clear and draw both PASS.
- `kmstest` (GBM + EGL + GLES2): the scanout BO is registered through ADDFB2 as `BGRX8888`,
  the format Mesa's big-endian GBM config reports. The bars were correct on screen, and the
  page-flipped cube gave 900 flips at 59.9 FPS with no flip errors.

### Behaviour change for clients

A client that labelled a host-order buffer as `XRGB8888` worked only by accident, and it
now shows wrong colours. That was kmstest's old workaround. On 019 it gave cyan, magenta,
white, blue instead of red, green, white, blue. Before 0037, ADDFB2 was refused on
big-endian, so the only way to hit this was a client that attempted ADDFB2 first. The right
labelling for a big-endian host-order buffer is `BGRX8888`, or plain legacy ADDFB.

Still open for #35: Mesa's GBM/EGL offers no `XRGB8888` visual on big-endian. Clients
like Xorg modesetting/glamor, which ask for one, still need to accept `BGRX8888`. The
acceptance items with Xorg or a Wayland compositor, mode switch and VT switch, are not
tested here.
