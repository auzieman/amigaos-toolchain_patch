# powerpc SPE: exec starts with a defined SPEFSCR (#48, #41) - 2026-11-17

## Problem

On e500v2, a program could start with every SPEFSCR exception enable clear. When it did:

- float Inf/NaN operands saturated instead of going through the kernel's IEEE fix-up:
  `(double)+Inf` gave `0x7fefffffffffffff` (DBL_MAX). dEQP's CPU reference then printed
  `0x1.fffffep1023` for Inf, and 274 `builtin_functions.precision.*` cases ended in
  QualityWarning (#48);
- double overflow in sqlite returned `1.79769313486232e+308` instead of `Inf` (#41).

The value a program started with depended on how it was launched. In 19 of 20 fresh ssh
sessions on kernel 019, the first command started with SPEFSCR `00100800` (enables clear),
and the second command in the same session started with `0000083c`.

## Cause

`start_thread()` (`arch/powerpc/kernel/process.c`, the `CONFIG_SPE` block) sets only the
saved copy, `current->thread.spefscr = 0`, and never writes the register:

1. `save_sprs()` stores the hardware SPEFSCR at the first switch-out. Until then the new
   image runs with whatever SPEFSCR its exec caller left, and that value is then saved as
   the image's own. `spe-execwith` shows this directly: set the register, exec, and read it
   in the new image (`hw/spefscr-019.txt`: `set 0` gives `00100800`, `set 2c` gives
   `0000082c`).
2. `flush_all_to_thread()` reads the hardware register only when MSR_SPE is set. A shell
   that forks right after exec, before it has used SPE, hands its child the saved `0`.

The `0` itself is also wrong. `INIT_THREAD` uses `SPEFSCR_INIT` (FINVE | FDBZE | FUNFE |
FOVFE, `0x3c`), and glibc's `fesetenv(FE_DFL_ENV)` sets `0x3c` on this board. The fix-ups
for Inf, NaN and denormal operands trap through those enables, so with them clear the
hardware's saturating results are what the program sees.

## Patch 0038 (against the kernel 019 tree)

`0038-powerpc-spe-exec-defined-spefscr.patch`, generated by `make-0038.py`. In
`start_thread()`, with preemption disabled, it sets the saved copy, `spefscr_last`, and the
register (when `CPU_FTR_SPE` is present) to FINVE | FDBZE | FUNFE | FOVFE. Nothing else
changes.

sets; `0x00220000` after a thread or fork is FINXS/FOVFS from the probe's arithmetic.

## dEQP

`qw48.txt` holds the 301 GLES3 cases that did not pass in the tabor3 mustpass run: the 274
`builtin_functions.precision.*` QualityWarnings, the 8 `common.fract.*_highp` Fails, and 19
other warnings. On 020, `qw48-plain.sh` ran them launched plainly (no wrapper), with
`deqp-gles3` carrying dEQP patch 0034. dEQP's own summary:

| Run | Pass | Fail | Warnings | Wall time |
|---|---|---|---|---|
| kernel 019, under `spe-execwith 3c` | 274 | 8 | 19 | 5 h 22 min |
| kernel 020, plain | 274 | 8 | 19 | 5 h 53 min |

All 274 precision cases pass. What is left is not this defect:

- The 8 `fract.*_highp` Fails come from the e500v2 zero sign in single-precision subtraction,
  which dEQP's CPU reference hits (#48 part 1).
- The 19 warnings are 18 line-rasterization cases and
  `fbo.completeness.samples.rbo1_rbo2_rbo4`. They warn the same way on 019 under
  `spe-execwith 3c`, so SPEFSCR does not cause them.

The precision cases are now slower, and dEQP's system time (9120 s at case 162) is higher than
its user time (8194 s). That is the kernel's SPE exception fix-ups, which now run where the
hardware returned saturated values before, and it is confined to dEQP's CPU reference.

`spe-execwith 0` cannot clear the enables on 020, because 0038 sets SPEFSCR at exec. So
`spe-cost.sh` clears them inside the process: `probes/spe-setfscr.c` is an `LD_PRELOAD` shim
whose constructor writes `$SPE_SETFSCR`, and threads created later inherit it. Each dEQP group
ran twice on the same boot (`hw/spe-cost-020.txt`):

| group | 0x3c (020): real / user / sys, s | enables clear: real / user / sys, s |
|---|---|---|
| `shaders.matrix.add.*` (324) | 29.50 / 29.98 / 1.12 | 29.89 / 30.52 / 0.89 |
| `texture.format.sized.2d.*` (112) | 6.89 / 6.53 / 0.32 | 6.87 / 6.46 / 0.39 |
| `texture.format.unsized.*` (64) | 6.30 / 5.57 / 0.67 | 6.30 / 5.60 / 0.63 |
| `fbo.blit.conversion.*` (437) | 54.34 / 52.06 / 1.57 | 54.36 / 52.02 / 1.62 |
| `rasterization.primitives.*` (10) | 2.84 / 2.65 / 0.17 | 2.84 / 2.64 / 0.19 |
| `precision.add.highp_vertex.*` (4) | 20.99 / 11.91 / 9.03, 4 Pass | 5.57 / 5.44 / 0.12, 4 QualityWarning |

Mesa's own CPU work (shader compiles, texture uploads, blits) costs the same either way. Only the
precision reference slows down, by 3.8x. With the enables clear its results are wrong again
(QualityWarning), which also shows that the shim took effect.

One fix-up costs about 0.93 us for a double operation and 0.56 us for a single one, against
3 ns for the same add without a trap (`probes/spe-trapcost.c`, `hw/trapcost-020.txt`). At that
rate, the 8.9 s of extra system time is about 10 million fix-ups for 4 cases. That is consistent
with interval arithmetic that carries Inf bounds through every operation. The SPE handlers call
no `PPC_WARN_EMULATED`, so no perf counter counts them directly.

## Files

- `0038-powerpc-spe-exec-defined-spefscr.patch`, `make-0038.py`: the patch and its generator.
- `build-020.sh`: the kernel 020 build, run inside `tabor-gcc14-spe-sdk:local`.
- `qw48.txt`, `qw48-plain.sh`: the 301-case list and the plain run on the board.
- `probes/`: `spe-thread.c` (SPEFSCR in main, a thread and a fork child), `spe-execwith.c`

  `spe-mainwatch.c` (LD_PRELOAD shim reporting SPEFSCR before main and at exit), `spe-setfscr.c`
  (LD_PRELOAD shim setting SPEFSCR), `spe-trapcost.c` (the cost of one fix-up).
- `spe-cost.sh`, `build-shim.sh`: the fix-up cost runs and the shim build.
- `hw/`: board output for 019 and 020.
