# glibc on e500v2: fmaf, ldexpf and asinf zero sign (#56) - 2026-11-18

## Problem

On the A1222 (P1022, e500v2), the SPE glibc 2.41 package returns +0 where IEEE 754 and C require
-0, and -0 where they require +0:

| call | e500v2 glibc | x86 glibc |
|---|---|---|
| `fmaf (-2, 1, 2)` | -0 | +0 |
| `fmaf (-1, 0, -0)` | +0 | -0 |
| `ldexpf (-0.0, n)`, every n | +0 | -0 |
| `asinf (-0.0)` | +0 | -0 |

The package is `results/glibc-002` on the build-server replica: Debian 2.41-12+deb13u4 with
`patches/glibc` 0001-0007. Its libm is `652b1e8a...`, the same as in the #27 and #38 hardware
bundles.

## Cause

e500v2 single-precision addition (`efsadd`) gives `(-0) + (-0)` as +0 and an exact cancellation the
sign of its first operand, in every rounding mode. The result is exact, so no SPE exception is
raised and the kernel's fix-up does not run. Double precision follows IEEE.

- `sysdeps/ieee754/dbl-64/s_fmaf.c`: for an exact zero, `if (temp == -z) return (float) temp + z;`
  converts `temp` to float and adds in float. In the installed libm that is `efscfd` then
  `efsadd` (`hw/fmaf-installed-objdump.txt`, `0xcbe90`/`0xcbe94`).
- `math/s_ldexp_template.c`: `if(!isfinite(value)||value==0) return value + value;`.
- `asinf` (`sysdeps/ieee754/flt-32/e_asinf.c`) returns `fmaf (x, 0x1p-25, x)` for tiny
  arguments, so it inherits the `fmaf` defect; it is correct once `fmaf` is.

## Patch 0008

`patches/glibc/0008-e500-float-zero-sign.patch`, generated by `make-0008.py` against the
glibc-002 source tree (after 0001-0007); `0008-origin.json` holds the baseline and patched file
hashes.

- `fmaf`: the exact-zero sum is formed in double, `return (float) (temp + z);`. `temp` is a
  double product, not a widened float, so GCC keeps the add in double (`efdadd`, then `efscfd`:
  `hw/fmaf-0008-objdump.txt`, `0xcbeb0`/`0xcbeb4`). The sum keeps the current rounding mode,
  which is the reason upstream has this path.
- `ldexp`: a zero is returned as it is, and a non-finite value still goes through
  `value + value`.

Both give the same values on an IEEE host.

## A1222 results (kernel 020)

`build-probe-gz.sh` links each probe with `/opt/gz/lib/ld.so.1` and an rpath of `/opt/gz/lib`.
That directory holds the three rebuilt files, so the probes run on the patched glibc and the
installed bundle is not touched. The same probe linked against the bundle gives the "installed"
column.

- **`probes/spe-libmzero.c`:** every libm function that Mesa's constant folding calls, over a grid
  of signed zeros, +-1, +-2, +-0.5, denormals, FLT_MAX, infinities and NaN (39,533 results),
  compared bit for bit with x86 (Debian glibc 2.41, GCC 14.2.0). `hw/libmzero-summary.txt`:

  | libm | differing from x86 |
  |---|---|
  | installed (`652b1e8a`) | 102: `fmaf` 94, `ldexpf` 7, `asinf` 1 |
  | with 0008 (`e4fc7e8d`) | 0; the output is byte-identical to x86's (`457b5112...`) |

- **`probes/spe-fmafmode.c`:** `fmaf`'s exact-zero results in all four rounding modes, plus
  `ldexpf (-0, 3)` and `asinf (-0)`. With 0008 the A1222 output equals x86's line for line
  (`hw/fmafmode-x86.txt`, `hw/fmafmode-a1222-0008.txt`). The installed glibc gives the same wrong
  value in every mode (`hw/fmafmode-a1222-installed.txt`).
