# qemu-user: PR_GET_FPEXC/PR_SET_FPEXC for PowerPC SPE (#39) - 2026-11-18

## Problem

qemu-user's `linux-user/syscall.c` answered `PR_GET_FPEXC` and `PR_SET_FPEXC` with `EINVAL`.
glibc's e500 `fegetenv` saves the environment as two words, the prctl mode and SPEFSCR, and
returns -1 without writing either when the prctl fails. libm's `sqrt` saves and restores the
environment, so its `fesetenv` loaded an uninitialised stack word into SPEFSCR. With the
0001-only build (`hw/qemu-fpexc-before-after.txt`):

```
after:  round=3 spefscr=0xd135c3 mul=1.79769e+308 third=0x1.5555555555555p-2
```

The stray FRMC bits switched the rounding mode to downward, and `1e308*10` gave DBL_MAX.

## Patch 0002

`patches/qemu/0002-linux-user-ppc-spe-fpexc-prctl.patch`, generated by `make-qemu-0002.sh`
with `edit-qemu-0002.py` from a clean 11.1.3 tree with 0001 applied. It keeps a per-thread
mode the way `arch/powerpc/kernel/process.c` keeps `thread.fpexc_mode`:

- on 32-bit, it starts as `MSR_FE0 | MSR_FE1`, so `PR_GET_FPEXC` gives `3`;
- `PR_SET_FPEXC` with `PR_FP_EXC_SW_ENABLE` stores SW_ENABLE plus the enabled exceptions,
  and masks off unknown bits;
- without SW_ENABLE it stores the classic FE0/FE1 mode, and returns `EINVAL` above
  `PR_FP_EXC_PRECISE`;
- new threads copy the parent's mode.

Only the mode is kept. qemu's SPE arithmetic gives IEEE results itself, so there is no kernel
fix-up or SIGFPE delivery for the mode to steer. CPUs without SPE keep `EINVAL`.

`check-qemu-series.sh` applies 0001 then 0002 to a clean `qemu-11.1.3.tar.xz` as
`scripts/build-qemu-ppc.py` does. The result is byte-identical to the tested tree.

## Results

`bench/spe-fpexc-prctl.c` (static, tabor3 SPE toolchain) runs the prctls, a thread, `fegetenv` and
`sqrt`. The same binary was run on the A1222 (kernel 020) and under both qemu-ppc builds
(`--target-list=ppc-linux-user`, `-cpu e500v2`).

| Check | A1222 kernel | qemu 0001 only | qemu 0001+0002 |
|---|---|---|---|
| `PR_GET_FPEXC` at start | `0x3` | `EINVAL` | `0x3` |
| set `0x20080`, get | `0x20080` | `EINVAL` | `0x20080` |
| `PR_GET_FPEXC` in a new thread | `0x20080` | - | `0x20080` |
| set `0xff0080`, get | `0x1f0080` | - | `0x1f0080` |
| set `2`, get / set `4` | `0x2` / `EINVAL` | - | `0x2` / `EINVAL` |
| `fegetenv` mode word | `0x3` | not written (`0x5a5a5a5a`) | `0x3` |
| SPEFSCR after `sqrt` (`docs/builds/gcc14-sbuild-20261116/hw/qemu-fpexc-sqrt.c`) | - | `0xd135c3` | `0` |
| `1e308*10` after `sqrt` | `inf` | `1.79769e+308` | `inf` |

`hw/board-fpexc-020.txt` has the A1222 run. `hw/qemu-fpexc-before-after.txt` has both qemu
builds.

`scripts/check-qemu-spe-fpexc.py` builds that probe with a given SPE compiler, runs it under a
given qemu-ppc, and requires the A1222's prctl answers, a written `fegetenv` mode word, and
`inf` after `sqrt`. It fails on the 0001-only build (11 of 12 checks false) and passes on
0001+0002 (`hw/check-qemu-ppc-0001.json`, `hw/check-qemu-ppc.json`).

Not modelled: the starting SPEFSCR. On the A1222 with kernel 020 (#48, patch 0038) a program
starts with `0x3c`, but qemu-user starts with `0`. The enables only route operations to kernel
fix-ups that qemu does not need, so results do not change.
